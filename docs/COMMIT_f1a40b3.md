## 1. 追加したローカルWebアプリ

`npm run local:start` で `http://localhost:4317` を開きます。入力欄、物語カード、実行ログ、HTML調査レポート、保存済み処理の履歴が一つの画面にあります。

URLを1行ずつ入力する、本文やHTMLを貼り付ける、複数の `.txt` / `.md` / `.html` / `.json` ファイルを選ぶ、という方法に対応します。合計1〜6件。JSONは見出しと本文、またはfacts配列を受け取ります。複数ニュースを一つの物語にまとめる選択肢もあります。

```text
URL・本文・HTML・ファイル
    ↓ 本文抽出
社会・産業インパクトの選別
    ├─ 該当なし → 選別結果を表示して終了
    └─ 通過 → 条件付きの物語を生成・表示
                    ↓ ユーザーが「調査する」を選択
               物語と根拠をJSONに保存
                    ↓ 独立したCLIプロセス
               Codexで一次資料を調査
                    ↓ 構造化JSON
               HTMLレポートを画面内に表示
```

`local/server.js` がWeb側の入口、`local/input.js` が入力処理、`local/generate.js` が選別と生成の接続を担当します。画面は `local/public/` のHTML/CSS/JavaScriptです。Node.jsの標準機能で動き、Supabaseや既存Next.jsの起動は必要ありません。

ただし生成時はOpenAI API、実調査時はCodex・Web検索に接続するため、AI処理も完全オフラインという構成ではありません。

## 2. 低インパクトニュースを先に除外

従来はニュースを0〜99点で比較して上位を選んでいました。その方式では、開催案内のような弱いニュースだけでも相対的な上位が生成対象になり得ました。

追加した `agents/impactPolicy.js` は各記事を次の4軸で0〜3点評価します。

| 評価軸 | 見るもの |
|---|---|
| 新規性 | 新しい決定・成果・段階への移行があるか |
| 変化の大きさ | 供給能力、費用、重要工程などを変え得るか |
| 波及範囲 | 複数組織や重要な供給工程へ影響が広がるか |
| 裏付け | 承認、実施内容、成果など具体的な根拠があるか |

全軸2以上、情報十分、実質的な変化という条件を満たすものだけ通過します。一つの軸が弱ければ、他軸の高得点で埋め合わせません。根拠の抜粋が実際の入力文に含まれるかもコードで確認します。同点や全件見送りを許容します。

同一URL等の完全重複を除き、8記事以内のバッチ内では同じ出来事の意味的重複も整理します。バッチ間の意味的重複は網羅的には除いていません。

この基準は研究中の仮基準です。取りこぼし率や予測精度を検証済みの閾値という意味ではありません。

## 3. 物語生成と企業調査の分担

ローカル版の生成プロンプトは `local/narrative-prompts.js` にあります。生成時は入力ニュースから1〜3段の短い経路を描きます。事実、未確認の波及仮説、成立条件、反証条件、次の調査質問をJSON上で分けます。

ニュースに直接書かれた会社の利益を言い換えるだけでなく、変化の先で必要になる工程・製品・事業上の役割を考えます。例えば「医療LLMを開発」から「電子カルテへの接続・導入支援が必要になる可能性」を描き、どの会社が受注したかは後段に残します。

この段階でテーマ純度や企業規模を詳しく調べたり、受注企業や数値を外部知識から補完したりはしません。計画を実績に、受注開始を受注確定に格上げしないよう指示します。筋の通る波及が描けないときは `abstain` で見送れます。根拠番号と見送り/連鎖の整合性をコードで検査しますが、毎回独立したAI評価役が品質を採点する仕組みは含まれていません。

## 4. 「調査する」からCLIへ渡す

カードの「調査する」は、その物語と根拠を `narrative-investigation/v1` 形式のJSONとして渡します。サーバーが `local/research-cli.js` を子プロセスとして起動し、そのCLIがさらにCodex CLIを起動します。ログはサーバーを起動したTerminalとWeb画面に表示されます。別のTerminal.appウィンドウを自動で開く実装ではありません。

調査指示は `skills/narrative-investigation/SKILL.md` です。IR、開示、発注・採択の資料など一次資料を中心に、以下を確認します。

- 発注・受注の証拠、過去の取引関係、製品の適合、未確認の区別
- 調査対象の会社と、上場親会社・関連会社の区別
- テーマ売上と同期間の連結売上によるテーマ純度
- 当該案件の年間寄与と会社全体の規模
- 因果距離、内製・代替・海外調達・既存設備での対応、反証

初回は最大2候補・5分、絞った検索を指示し、Webツールイベントにも上限を設けます。モデルが検索を一イベントにまとめる場合があるため、イベント数と検索クエリ数は必ずしも一致しません。

数値が確認できない場合はnullで残し、HTMLでは算定不可と表示します。期間・会計範囲・単位・テーマ適合・出典が揃う場合だけ比率を表示します。調査は実行時点の資料を使うので、過去時点の情報だけを使うバックテストとは異なります。

Codexの構造化JSONを `local/report.js` でHTMLへ変換します。AIが生成した任意のHTMLをそのまま実行する方式ではありません。文字列をエスケープし、レポートをsandbox iframeに表示します。agentcastの実行ログとHTML成果物を並べる考え方を参考にしています。

## 5. 単体CLIとスキル

Web画面から保存したJSONをCLIでも使えます。

```sh
npm run investigate -- --input /absolute/path/story.json --output /absolute/path/new-report --ack-usage
```

`report.json`、`report.html`、`events.jsonl` と入力・スキーマを保存します。`--demo` なら外部調査なしの架空データで接続を確認できます。出力先は毎回新しいフォルダにします。

`npm run skill:install` はリポジトリ内のスキルをCodexのスキルディレクトリにリンク登録します。これによりWeb画面を使わず、`$narrative-investigation` やスキル付属CLIからも同じ手順を利用できます。

## 6. 保存と費用

入力・途中結果・ジョブ状態・イベントログ・結果は `local/data/jobs/<id>/` に保存します。履歴から再表示でき、再起動時には実行中のジョブを中断として扱います。自動再試行はしません。一度に実行できるジョブは一つです。

生成APIは研究用の累計1,600円相当の台帳で管理します。APIを呼ぶ前に保守的な上限額を予約し、利用トークンが分かれば精算します。既存研究台帳があれば引き継ぎ、研究フォルダがない新規環境ではローカル台帳を作ります。請求額を厳密に再現する会計システムではなく、余裕を取った予算制御です。

CLI調査は既存Codexログインを使います。接続確認時はChatGPT側の利用枠を使っており、生成APIの台帳とは別でした。

URL取得では内部ネットワークへの接続を拒否し、HTMLから本文だけを抽出します。静的HTML/テキスト向けで、ログイン必須ページ、PDF、JS描画ページなどには対応していません。
